# 受領モデルのローカル推論検証

## 結論

受領された `serve.py`、`model/ra_screening_model.pt`、`requirements.txt` は、同梱5画像をローカルで推論するために必要な一式として揃っている。元ファイルを修正せず、全画像で11関節の推論とJSON化に成功した。追加の学習コード・重みの提供は今回の動作確認には不要。ただし判定精度や学習時と完全に同じ推論であることを確認するための資料は不足している。

HTTP API、Docker、Cloud Runの実装・デプロイは行っていない。Linux上の動作は未検証。

## 実行環境と結果

macOS arm64、Python 3.11.13、CPU、PyTorchスレッド数4。依存関係は元のrequirements.txtから専用 `.venv` に導入。実際の全バージョンは `requirements-tested-macos-py311.txt` に保存（Linux向けロックファイルではない）。

全画像で結果のwarningsは空。ライブラリ側の非推奨警告等はrun.logに記録。時間は画像ファイル読込後の前処理＋推論であり、Cloud Runの性能予測ではない。sample_001の再実行で関節確率の最大差は0。白紙画像も追加で検証した。

- チェックポイント：epoch、model、extraを保持。state_dictは346エントリ、パラメータ数23,184,911。
- strict=Trueでmissing_keys / unexpected_keysともに空。全保存テンソルが有限値。
- 関節しきい値：0.47512562814070347、手しきい値：0.4796482412060301。0.5を使うと判定が変わるため保存値を維持する必要がある。
- ResNet18、GNN hidden=320、RGB入力、256×256、RGE・CBAM等の設定を保存済み。
- weights_only=Trueで正常読込。任意の追加Pythonクラスの許可やweights_only=Falseへの変更は不要。
- ResNet18はweights=Noneで構築され、推論時のImageNet重みダウンロードは不要。MediaPipeの検出モデルはインストール済みパッケージに含まれるもので動作した。
- 検証プロセスの最大RSSは約1.55 GiB。重み整合性確認用モデルも同一プロセス内で構築しているため、本番の必要メモリそのものではない。
- macOSの実行サンドボックス内ではMediaPipeがNSOpenGLPixelFormatの生成に失敗。制限外のローカル実行では成功。モデル重みの問題ではなく、このMacの実行環境による差。

## 問題と確認事項

### 1. 手が未検出でもfalseを返す（実測）

serve.py:534–539。白紙画像の結果はra_detected=false、hand_probability=0.0、num_joints_detected=0、warnings=["No hand detected in image."]。
これは陰性を推論した結果ではなく、モデルを実行していない結果。後で利用側がfalseだけを参照すると誤解する。将来のAPIでは判定不能の状態を区別すべき。

### 2. 正解ラベル・正式な期待出力がない

全5枚がモデル上は陽性になったが、それが正しいかを照合できる関節ラベル・手レベルラベルが同梱されていない。READMEの出力例は一部省略された説明用データ。今回保証できるのは処理が完走し整合した数値を出すことまで。確率が狭い範囲に集中することだけで学習不良とは断定できない。

先方には5枚の正式な期待出力（許容誤差付き）、関節・手の正解ラベル、可能なら陰性例と手未検出例の提供を依頼すると受入判定が明確になる。実画像の評価結果、しきい値の選定根拠、学習・検証版の識別情報も精度評価には必要。

### 3. 学習側と同一であることは独立検証できない

serve.pyにはtrain_eval.py / prepare_real_dataset.pyと同じという記載があるが、その元コードは非同梱。重みの名前・形状の一致は確認できても、クロップ・色変換・グラフ・forward処理が学習評価時と同一かは断定できない。元コード全体がなくても、先方の同じ画像に対する参照出力があれば照合できる。

### 4. 再現用のPython・依存バージョン指定が不足

requirements.txtは多くが下限だけの指定で、インストール時点により構成が変わる。今回はPython 3.11で成立したが、READMEの「Python 3.9以降」が全ての新しいPythonで動くことを意味するとは確認できない。先方の検証済みPythonと依存関係一式を受領するのが望ましい。

このチェックポイントは現在のweights_only=Trueで読める。PyTorch 2.6で既定値が変更されたことは公式にも記載されているが、今回この互換性エラーは発生しなかった：https://pytorch.org/blog/pytorch2-6/

### 5. 入力条件と説明の細部

- EXIF回転を適用するImageOps.exif_transposeの処理がない。今回のJPEGにはOrientationタグがないため影響しなかったが、スマートフォン画像は別途確認が必要。
- max_num_hands=1であり、両手画像や手の甲・掌・左右を厳密に検証する処理はない。部分遮蔽の関節を確実に除外する実装でもない。READMEの片手入力条件を明確に維持する必要がある。
- READMEはモデルforwardがシグモイド後の確率を返すと説明しているが、実コードのforwardはlogitを返し、サービス側serve.py:559でsigmoidを適用する。現在の公開サービス呼出しは正しいが、直接モデルを呼ぶ実装では注意。
- 背側パッチ欠如時の説明は「自己参照」だが、実装は参照パッチとの差分をとらずr-max(g,b)を使う。また背側クロップ領域が無効になった場合の警告が網羅されていない。今回5枚ではこの問題は発生していない。

## 再実行

ディレクトリ直下で以下を実行する。

```sh
.venv/bin/python validation/run_local.py
```

元の推論コードを直接インポートし、重み整合性、5画像の11関節検出、値域、しきい値整合性、再実行、白紙入力を確認する。結果は `validation/results.json` に保存。元のserve.py、重み、README、requirements.txt、test.sh、画像は変更していない。
